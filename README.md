# 블러피 — 링크로 즐기는 2~5인 카드 베팅 대결

방 생성자가 모드를 골라 방을 만들고 링크를 공유하면, 들어온 사람들이 한 테이블(2~5명)에 모여 가상 칩을 걸고 대결합니다. 방장이 마음대로 시작하고, 방 안에서 누적 칩 수익으로 랭킹을 매깁니다.

> 칩은 **가상의 무료 포인트**입니다. 현금·경품·충전·환전·거래 기능은 없습니다.

- 프론트엔드: Vite + React + TypeScript, React Router, Tailwind CSS, React Three Fiber (3D 카드)
- 백엔드: **서버 코드 없음.** Supabase(Anonymous Auth, Postgres, RLS, Realtime Broadcast, RPC)만 사용. 무료 플랜으로 동작
- 배포: Vercel (SPA 리라이트 포함)

## 이 프로젝트의 DB 객체 이름 규칙 (다른 게임과 같은 Supabase 프로젝트 공유)

같은 프로젝트에서 다른 게임(가위바위보)과 함께 쓸 수 있도록 **이 게임이 만드는 모든 객체는 `card_` 접두어**를 가집니다.

| 종류 | 이름 |
| --- | --- |
| 테이블 | `card_rooms`, `card_players`, `card_matches`, `card_match_players`, `card_hands`, `card_hand_seats`, `card_actions` |
| RPC | `card_create_room`, `card_get_room_view`, `card_join_room`, `card_my_status`, `card_heartbeat`, `card_queue_match`, `card_start_match`, `card_leave_match`, `card_get_visible_hand`, `card_get_match_state`, `card_act`, `card_timeout_check`, `card_advance_match`, `card_verify_admin`, `card_close_room` |
| 내부 스키마 | `card_game` (클라이언트 접근 불가) |
| 인덱스 | `card_*` |
| Realtime 토픽 | `card_room:<id>`, `card_match:<id>` |

마이그레이션은 **기존 객체를 DROP/ALTER/REPLACE 하지 않습니다.** `create table` / `create function`(`or replace` 없음) / `create schema`(`if not exists` 없음)만 쓰므로, 같은 이름이 이미 있으면 덮어쓰지 않고 오류로 멈춥니다. 권한 `revoke`/`grant` 도 이 게임의 객체에만 하나씩 지정합니다(스키마 전체 대상 구문 없음). 이 동작은 테스트(`src/db/coexist.test.ts`)로 검증합니다. 기존 `rooms`, `create_room`, `act`, `game` 스키마가 있는 DB에 적용해도 데이터·권한·구조가 그대로입니다.

> **이미 이전(1:1) 버전 SQL 을 실행했다면**: 새 마이그레이션은 기존 `card_*` 를 덮어쓰지 않습니다. `supabase/dev_reset_card_objects.sql` 을 한 번 실행해 `card_*` 객체만 지운 뒤(데이터 삭제됨, 다른 게임 객체는 그대로) 0001 → 0004 를 다시 실행하세요.

## 시작하기

### 1. Supabase 설정
1. [supabase.com](https://supabase.com)에서 프로젝트를 만듭니다(무료 플랜 가능). 가위바위보와 같은 프로젝트를 써도 됩니다.
2. **Authentication → Sign In / Providers → Anonymous Sign-Ins** 를 **켭니다.** (꺼져 있으면 입장할 수 없습니다)
3. (권장) Authentication의 CAPTCHA/Rate limit 설정으로 익명 가입 남용을 막습니다.
4. Realtime 은 기본값(Broadcast 사용 가능) 그대로 두면 됩니다. 이 앱은 DB 변경 스트림을 쓰지 않고, DB가 보내는 "바뀌었다" 신호(Broadcast)만 받습니다. 신호가 끊겨도 3~5초 폴링으로 동작합니다.

### 2. SQL 실행
Supabase **SQL Editor**에서 아래 파일을 **순서대로** 실행합니다.

1. `supabase/migrations/0001_schema.sql` — 테이블, 제약, RLS, 권한
2. `supabase/migrations/0002_game_engine.sql` — 덱 섞기, 베팅 검증, 승패 판정, 사이드 팟, 칩 계산(내부 함수)
3. `supabase/migrations/0003_rpc.sql` — 클라이언트용 RPC 와 실행 권한
4. `supabase/migrations/0004_spectate.sql` — 관전(읽기 전용) RPC: `card_list_tables`, `card_spectate_match`

(Supabase CLI를 쓴다면 `supabase db push`.) 한 번만 실행하세요. 다시 실행하면 이미 있는 객체 때문에 오류로 멈추며, 기존 객체는 변경되지 않습니다.

### 3. 환경변수
```bash
cp .env.example .env
```
`.env` 에 **Project Settings → API** 의 값을 넣습니다.
```
VITE_SUPABASE_URL=https://xxxx.supabase.co
VITE_SUPABASE_ANON_KEY=<anon public key>
```
**`service_role` 키는 절대 프론트엔드에 넣지 마세요.** 이 앱에는 필요 없습니다.

### 4. 로컬 실행
```bash
npm install
npm run dev        # http://localhost:5173
npm test           # 규칙/DB 테스트
npm run build      # 타입체크 + 프로덕션 빌드
```
혼자 테스트하려면 브라우저를 여러 개(시크릿 창 포함) 열어 같은 방 링크로 들어가세요. 창마다 다른 참가자가 됩니다.
개발 서버에서는 `/demo` (좁은 폭 확인은 `/demo?w=360`)로 Supabase 없이 3D 카드 연출을 미리 볼 수 있습니다(프로덕션 빌드에는 포함되지 않음).

### 5. Vercel 배포
1. GitHub 에 푸시하고 Vercel 에서 저장소를 Import (Framework: Vite 자동 인식).
2. **Environment Variables** 에 `VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY` 를 등록.
3. Deploy. `vercel.json` 의 리라이트가 `/r/:id` 같은 경로를 SPA 로 처리합니다.
4. OG 이미지(`public/og.svg`)는 일부 메신저가 SVG 를 지원하지 않습니다. 1200×630 PNG 로 교체하고 `index.html` 의 `og:image` 를 절대 URL(`https://내도메인/og.png`)로 바꾸면 링크 미리보기가 가장 안정적입니다.

## 화면

| 경로 | 설명 |
| --- | --- |
| `/` | 소개, 방 만들기, 30초 규칙 (첫 방문 시 자동 안내) |

## 게임 규칙

### 테이블(매치)
- 방에서 **"대결 찾기"** 를 누르면 대기 중인 테이블(5명 미만, 먼저 열린 순)에 앉습니다. 대기 테이블이 없으면 새 테이블이 열리고, **그 사람이 방장**이 됩니다.
- 방장은 **2명 이상이면 언제든 "지금 시작하기"** 를 누를 수 있습니다. 더 기다려도 되고, **5명이 모이면 자동으로 시작**합니다.
- 방장이 나가면 다음 사람이 방장이 됩니다. 아무도 없으면 테이블이 닫힙니다. 30초 넘게 신호가 없는 대기자는 자동으로 자리에서 빠집니다.
- 매치가 끝나면 다시 "대결 찾기"로 다른 테이블에 앉을 수 있습니다.

### 모드 (방 생성 시 선택, 방 안의 모든 대결에 동일)
- **A 모드(반공개)**: 각자 카드 2장 중 1장은 공개, 1장은 비공개. 나는 내 카드 2장 + **각 상대의 공개 카드 1장**을 봅니다.
- **B 모드(눈치)**: 나는 **모든 상대의 카드 2장**을 보고, 내 카드는 보지 못합니다(내 카드는 "?" 뒷면으로 이마에 붙은 연출).
- 두 모드 모두 **한 판이 끝나면(쇼다운이든 모두 다이든) 그 판에 참여한 모든 좌석의 카드가 공개**됩니다. 진행 중에는 모드별 규칙대로 숨깁니다. 결과 화면 유지 시간은 쇼다운 6초, 다이로 끝나면 4초입니다.

### 한 판
- 덱: 1~10 카드 두 벌(20장). 매 판 새로 섞어 칩이 남은 사람에게 2장씩(최대 5명 = 10장).
- 족보: **페어(같은 숫자 2장) > 합이 큰 쪽.** 페어끼리는 숫자가 큰 쪽 승리. 완전히 같으면 동점자끼리 판돈을 나눕니다(남는 칩은 다음 판 판돈으로 이월).
- 시작 시 칩이 있는 모두가 기본 판돈 1칩.
- 선 플레이어부터 시계방향(좌석 순)으로 행동합니다. 선은 판마다 한 칸씩 이동합니다.
- 행동: **체크**(올린 금액이 없을 때만) / **베팅·레이즈**(1~3칩) / **콜**(맞추기) / **다이**(판돈 포기).
- **레이즈가 나오면 이미 콜/체크한 사람도 다시 행동**합니다. 남은 사람이 모두 같은 금액을 맞추거나 다이하면 판이 끝납니다. 전원이 체크하면 쇼다운.
- 한 판에 베팅/레이즈는 총 3회까지. 턴 제한 20초 — 초과 시 체크 가능하면 체크, 아니면 다이.
- **승부(쇼다운)에 남은 사람 중 최고 족보가 판돈을 독식**합니다. 모두 다이하고 한 명만 남으면 그 사람이 판돈을 가져갑니다.
- **올인**: 가진 칩보다 많이 걸 수 없고, 칩이 모자라면 남은 칩 전부로 콜(올인)할 수 있습니다. 올인한 사람은 **자기가 낸 금액의 배수까지만**(사이드 팟) 가져갑니다. 예) 3칩 올인한 사람이 최고 족보여도, 다른 두 명이 6칩씩 걸었다면 메인 팟(3×3)만 가져가고 나머지는 나머지 둘 중 승자가 가져갑니다.

### 매치와 랭킹
- 각자 시작 칩 **100개**, 최대 **10판**. 칩이 0이 되면 **탈락**(이후 판에는 카드를 받지 않고 구경), 한 명만 칩이 남으면 즉시 종료.
- 종료 시 **칩이 가장 많은 사람이 승리**(동점이면 공동 승리). **(최종 칩 − 100)** 이 방 누적 수익에 더해집니다. 다음 매치는 다시 100칩으로 시작.
- 랭킹: 누적 수익 ↓ → 승리 매치 수 ↓ → 먼저 참여한 순.
- 방 종료는 생성자만(관리 링크의 토큰, DB 에는 SHA-256 해시만 저장). 대기/진행 중인 테이블은 무효 처리(수익 미반영)되고 최종 순위가 확정됩니다.

### 규칙이 모호해서 임의로 정한 부분
1. **방장**: "먼저 대결 찾기를 눌러 테이블을 연 사람"을 방장으로 정했습니다. (방 생성자와는 별개입니다. 방 생성자는 관리 화면에서 방 종료만 할 수 있습니다.)
2. **자동 합류**: 대결 찾기는 5명 미만인 가장 먼저 열린 대기 테이블에 자동으로 앉습니다. 테이블을 고를 수는 없습니다.
3. **레이즈 횟수**: 첫 베팅도 1회로 셉니다(베팅/레이즈 합쳐 판당 최대 3회). 3회가 나오면 나머지는 콜/다이만 가능.
4. **레이즈 금액**: "올림 금액"이 1~3칩이며, 레이즈는 현재 최고 금액을 맞춘 뒤 그 위에 올립니다(콜 금액 + 올림 금액을 냄). 올림 금액은 `min(3, 내 칩 − 콜 금액)` 으로 제한됩니다.
5. **기본 판돈으로 칩이 0이 되면** 그 사람은 올인 상태입니다. 행동할 수 있는 사람이 1명 이하면 베팅 없이 곧바로 쇼다운합니다.
6. **동점/이월**: 동점자끼리 나누고 남는 칩(나머지)은 다음 판 판돈에 합칩니다. (이월 칩이 있는 채로 매치가 끝나면 그 칩은 소멸)
7. **매치 승자**: 나가지 않은 사람 중 최종 칩이 가장 많은 사람. 동점이면 공동 승자(각자 승리 1회). 칩이 같아도 0이면 탈락자입니다.
8. **나가기/무응답**: `나가기`는 기권. **60초 넘게 응답이 없는**(연결 유지 신호 중단) 사람도 기권 처리됩니다. 기권한 사람은 그 판에서 다이 처리되어 이미 건 칩을 잃고, 이후 판에서 제외되며, **수익은 `min(최종 칩 − 100, 0)`** 이라 이득을 챙길 수 없습니다(앞서다 나가서 수익을 챙기는 것 방지). 나머지가 계속 진행하고, 남은 사람이 1명이 되면 종료됩니다.
9. **연출 시간**: 판이 끝나면 다음 판 시작 전에 쇼다운 6초 / 다이 2초의 결과 연출 시간이 있습니다.
10. **A 모드의 공개 카드**: 매 판 서버가 각자 2장 중 어느 1장을 공개할지 무작위로 정합니다.
11. **베팅 크기**: 칩이 100개로 늘었지만 베팅/레이즈는 1~3칩 그대로라서 한 판에 잃는 칩은 많지 않습니다(칩이 0이 되는 탈락은 드뭅니다). 판당 크기를 키우려면 `0002_game_engine.sql` 의 `least(3, ...)`, 레이즈 상한과 `src/game/rules.ts` 의 `MAX_RAISE_AMOUNT` 를 함께 바꾸면 됩니다.
12. 닉네임은 방 안에서 대소문자 구분 없이 유일해야 하며 1~12자입니다. 한 방은 최대 200명. 같은 브라우저(익명 계정)가 다시 들어오면 기존 참가자로 복귀합니다. 시크릿 창/다른 기기는 다른 참가자입니다.
13. **탈락/관전/다이한 사람의 시야**: 칩이 없어 탈락했거나 이번 판을 쉬는 사람, 다이한 사람도 같은 모드 규칙으로 보입니다. B 모드에서는 다른 사람들의 카드가 그대로 보입니다(오프라인에서 다이한 사람도 이마 카드를 보는 것과 같음). 따라서 B 모드에서 탈락자가 몰래 내 카드를 알려주는 것은 막을 수 없습니다(보안 설계의 한계 참고).

## 관전

방에 닉네임으로 입장한 사람은 로비의 "진행 중인 테이블"에서 👀 관전할 수 있습니다. 관전자는 좌석·칩·판돈·차례·행동 로그와 **이번 판에 참여 중인 모든 좌석의 카드**를 봅니다. 관전자는 행동·시작·나가기를 할 수 없습니다. 관전자가 참가자에게 카드를 몰래 알려주는 것은 서버가 막을 수 없는 부정행위이므로, 같은 방 사람끼리의 신뢰가 전제입니다. 검증: `src/db/spectate.test.ts`.

## 보안 설계

핵심: **숨겨야 할 카드 값은 어떤 경로로도 브라우저에 전달되지 않습니다.**

- 덱 섞기·카드 배분·베팅 검증·승패 판정·사이드 팟 계산·칩 계산은 모두 Postgres `security definer` 함수에서만 합니다. 덱은 `gen_random_uuid()`(CSPRNG) 기준 정렬로 섞습니다.
- **클라이언트는 테이블에 직접 접근할 수 없습니다.** 7개 테이블 모두 RLS 를 켜고 정책을 만들지 않았으며, `anon`/`authenticated` 의 테이블 권한도 회수했습니다(이중 차단). 읽기·쓰기는 전부 RPC 로만 합니다. 카드는 `card_hands.deck` 과 `card_hand_seats.cards` 에만 있고 어떤 정책·권한으로도 SELECT 되지 않습니다.
- 카드는 `card_get_visible_hand(match_id)` 로만 조회하며, 모드와 요청자(`auth.uid()`)에 따라 볼 수 있는 카드만 돌려줍니다(못 보는 카드는 `null`).
  - A: 내 카드 2장 + 각 상대의 공개 카드 1장 / B: 모든 상대의 카드 2장(내 카드 `null`) / 판 종료 후: 그 판 참여자 전원의 카드(다이한 사람 포함)
- `card_get_match_state` 등 카드 외 RPC 는 카드·덱 컬럼을 읽지 않고, 다른 사용자의 `uid` 도 노출하지 않습니다.
- Realtime 은 **Broadcast 신호**("changed")만 씁니다. 페이로드에는 시각만 있고 카드·칩 값이 없으며, 클라이언트는 신호를 받으면 RPC 로 다시 조회합니다. (DB 변경 스트림 `postgres_changes` 는 쓰지 않습니다.)
- 턴 순서, 금액, 레이즈 횟수, 20초 제한, 무응답 기권, 방장 권한(시작)은 서버가 검증합니다. 클라이언트의 버튼 활성화는 같은 규칙을 계산한 편의 기능일 뿐이며, 서버가 규칙에 맞지 않는 요청은 예외로 거부합니다.
- 내부 함수는 `card_game` 스키마에 있고 클라이언트에 USAGE 권한이 없습니다. 공개 RPC 는 `anon` 과 `PUBLIC` 의 실행 권한을 회수하고 `authenticated`(익명 로그인 사용자 포함)에만 엽니다.
- 방 관리 토큰은 `card_create_room` 응답에서 한 번만 원문이 반환되고 DB 에는 SHA-256 해시만 저장됩니다. 토큰은 URL fragment(`#t=`)로 전달되어 서버로 전송되지 않으며, 접속 후 주소창에서 지워집니다.

한계: 익명 로그인이라 한 사람이 여러 브라우저 프로필로 여러 계정을 만들 수 있습니다(가상 칩·랭킹이므로 허용). 같은 테이블에 같은 사람의 여러 계정이 앉으면 정보를 공유할 수 있습니다(B 모드에서 특히). 방 생성/입장에 대한 서버측 속도 제한은 없으니 필요하면 Supabase Auth 의 rate limit/CAPTCHA 를 켜세요.

DB 테스트는 [PGlite](https://pglite.dev)(WASM Postgres)에 `supabase/migrations/*.sql` 을 그대로 적용해 실행하므로 로컬에 Postgres/Docker 가 필요 없습니다. Supabase 가 제공하는 `auth.uid()`, `anon`/`authenticated` 역할, 기본 권한, `realtime.send` 는 `src/db/harness.ts` 가 흉내 냅니다.
